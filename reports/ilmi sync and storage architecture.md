# Keep the Markdown, move the bytes

The claim that "Markdown files won't cut it, SQLite is the only reasonable way" is wrong for ilmi, and the best architecture is the one ilmi mostly has: **Markdown stays the source of truth, git stays the sync for text, and PDFs and ink move out of git into a content-addressed store on an S3-compatible bucket that each device downloads lazily**. A SQLite database belongs in ilmi only as a per-device, deletable index, built when device measurements call for it. The thread's central premise, one file per card, does not describe ilmi: 66 files hold the sample's 758 cards, 10,000 one-card files parse in 44 ms, and the sample opens in about 35 ms. The costs the measurements did expose are in-memory and independent of the storage format: the whole queue is rebuilt twice per grade, one tree lookup is quadratic, and the renderer holds 3.7 times the vault's Markdown bytes in heap. cr-sqlite, the thread's proposed sync, has had no release since January 2024 and merges by a per-cell last-write-wins rule, which is weaker than the format-aware merge ilmi already ships. The thread is right about two things: a full-text index is far faster than a scan, and conflict handling is hard. Every timing here comes from an M5 Mac under Node with a warm file cache; nothing has run on an iPad or iPhone, and that gap decides the order of work.

## The claim fails on ilmi's format and on its numbers

The table gives the verdict on each point in the pasted thread; the paragraphs after it carry the evidence.

| The thread's point | What ilmi's evidence shows | Verdict for ilmi |
|---|---|---|
| Offline-first on mobile, web and desktop means SQLite | ilmi has no browser target, and the argument assumes client state must be a database | Does not apply |
| Parsing 10,000 Markdown files for due dates ends badly | A card is a paragraph, not a file; 10,000 one-card files parse in 44 ms | Wrong on the Mac, unproven on a phone |
| Full-text search needs SQLite | FTS5 answers in under 1 ms where a scan takes 5–40 ms, but its stock tokenizers miss voweled Arabic | Right about speed, as a derived index only |
| Relational joins need SQLite | ilmi has no note-type entity; its queries are scans costing 5 ms at 758 cards | Not applicable below about 100,000 cards |
| Caching is a last resort | ilmi's in-memory state is already a cache with a trusted invalidation rule | Fair warning, wrong conclusion |
| cr-sqlite gives peer-to-peer CRDT sync | Unreleased since January 2024; merges per cell by edit count | Wrong choice in 2026 |
| Last-write-wins is not conflict handling | True, and cr-sqlite is last-write-wins per cell | Right, and it favours ilmi's merge |
| Anki search is slow because it uses LIKE | Anki does use LIKE; a LIKE scan of 100,000 cards took 37 ms | True fact, weak argument |

### A card is a paragraph, and 10,000 files parse in 44 ms

The thread assumes one Markdown file per card. In ilmi a card is a paragraph inside a document and its schedule is one comment line beneath it; a deck is one file ([FORMAT.md](../FORMAT.md)). The sample vault holds **758 cards in 66 Markdown files (654 KB)**, and its largest deck is one 32 KB file with 178 cards ([measured for the notes](../research_notes/ilmi%20sync%20and%20storage%20architecture/ilmi_current_storage_and_load_timing.md)). Under the thread's own assumption, 10,000 one-card files parse in 44 ms and open end to end in 0.76 s, of which 277 ms is a lookup bug described below. A vault with ilmi's real shape and 10,000 cards is about 870 files and opens in roughly 0.3 s. Ten thousand sample-shaped files are a different animal: they hold **115,000 cards and 100 MB of text, open in 3.5 s and occupy 381 MB of heap** ([measured for the notes](../research_notes/ilmi%20sync%20and%20storage%20architecture/ilmi_current_storage_and_load_timing.md)). A second, independent measurement agrees: reading 10,000 deck files holding 100,000 cards and extracting every due date took 0.25–0.29 s ([measured for the notes](../research_notes/ilmi%20sync%20and%20storage%20architecture/sqlite_and_crdt_sync.md)). The honest limit on these figures is that they exclude Tauri's per-file IPC, a cold disk and a phone's slower engine, so "wrong on the Mac, unproven on a phone" is the accurate verdict.

The "web" in the thread's first point is what forced its author's hand. Pentive is a browser app, so it needs SQLite compiled to WebAssembly; its own design notes concede that SQLite on a real file system would perform better ([Pentive design decisions](https://github.com/AlexErrant/Pentive/blob/main/design-decisions/frontend.md)). ilmi's Rust side can link native SQLite on Mac and iOS whenever it wants one, so nothing about the platform list pushes the source of truth into a database.

### An index is a speed-up, and FTS5 breaks voweled Arabic by default

The thread is right that an index beats a scan by two to three orders of magnitude: at 100 MB of Markdown, SQLite's FTS5 answered in 0.01–0.66 ms where a `LIKE` scan took 33–53 ms. The scan it replaces is already small at ilmi's sizes, though: a substring scan of all text took **5–40 ms at 100 MB** and under 1 ms on the sample ([measured for the notes](../research_notes/ilmi%20sync%20and%20storage%20architecture/ilmi_current_storage_and_load_timing.md)). The larger problem is correctness. FTS5's default `unicode61` tokenizer treats Arabic vowel marks as separators, so كَرَم is indexed as three one-letter tokens and a search for كرم finds nothing. Even over text pre-folded by ilmi's own rule, `unicode61` found the word in 2 of the 5 sample files that ilmi's substring search finds, because it matches whole tokens and misses prefixed and suffixed forms. Only the `trigram` tokenizer over pre-folded text matched all 5, at an index 3.7 times the size of the Markdown ([measured for the notes](../research_notes/ilmi%20sync%20and%20storage%20architecture/ilmi_current_storage_and_load_timing.md)). Pentive reached the same place: its FTS5 tables use `trigram` over an app-defined normalising function and are derived, trigger-maintained indexes, not replicated data ([Pentive init.sql](https://github.com/AlexErrant/Pentive/blob/main/shared/sql/init.sql)). The thread's Anki fact is accurate, since Anki builds text search as `LIKE '%term%'` ([Anki sqlwriter.rs](https://github.com/ankitects/anki/blob/main/rslib/src/search/sqlwriter.rs)), but a 37 ms scan of 100,000 cards is not why anyone should change their file format.

### Joins and caches: the relations are already in the file

The join the thread has in mind is Anki's four normalised tables. ilmi has no note-type entity at all: a card's form is read from its text, and document, section, card and schedule are related by position, path and id ([FORMAT.md](../FORMAT.md)). Every cross-entity query is an in-memory scan, and the measured cost is 5 ms for the queue at the sample's size, 75 ms at 11,000 cards and about 1 s at 115,000. Filtering 100,000 in-memory card records for due cards took 1.9 ms against 1.0 ms for the indexed SQL query ([measured for the notes](../research_notes/ilmi%20sync%20and%20storage%20architecture/sqlite_and_crdt_sync.md)). Joins start to pay for queries that cross documents on non-hierarchical keys at scale, such as leech analysis over a decade of reviews, and a derived index answers those without owning the data.

"Caching is a last resort because invalidation is hard" is a fair general warning that lands oddly on ilmi. The in-memory `Vault.cache` is already a cache, invalidated by an mtime-and-size stamp and by watcher events, and the app trusts that rule for correctness today ([src/vault/vault.ts](../src/vault/vault.ts)). A persistent index extends the same rule across launches. The cautionary tale the thread would reach for cuts the other way: Obsidian's 315-second loads and half-hour re-indexing at 87,000 files came from its IndexedDB cache failing to flush to disk, a cache-persistence bug and not a limit of parsing Markdown ([Obsidian forum](https://forum.obsidian.md/t/unpractical-vault-load-time-for-large-vaults-on-mobile-indexeddb-transactions-are-not-flushed-to-disk/88470)).

### cr-sqlite is the last-write-wins the thread objects to

A CRDT is a data structure that two devices can edit independently and always merge without a server. cr-sqlite applies the idea per table cell, and its rule is "biggest `col_version` wins", where the version is a count of edits to that cell ([Corrosion docs](https://superfly.github.io/corrosion/crdts.html)). That keeps two devices' edits to different columns of one row, which is better than Anki's whole-row rule. For the same cell it keeps one value and discards the other silently, and the winner is the device that edited more often, not the one that reviewed most recently. With `due`, stability and difficulty in separate columns, a merge can combine one device's `due` with the other's stability into a schedule neither device computed. The README says rich-text CRDTs "are still being implemented", so prose would get no merge at all ([cr-sqlite README](https://github.com/vlcn-io/cr-sqlite)).

The project's state settles the matter. The last upstream release is **v0.16.3 from 17 January 2024**; `main` took 13 commits in 2024 and none in 2025; the author said in December 2024 that he is "full time on" another product and expects no spare capacity "for at least 1-2 years" ([cr-sqlite issue #444](https://github.com/vlcn-io/cr-sqlite/issues/444)). The live fork is Fly.io's, tuned for a thousand-node server mesh. Pentive itself is pinned to a 2023 build of the library, has never had a release, and has had no commits since March 2025 ([Pentive](https://github.com/AlexErrant/Pentive)). The author's current employer makes the sharpest counter-argument: Zero's documentation says of offline conflicts that "no sync engine or CRDT algorithm can automatically solve it for you" ([Zero docs](https://zero.rocicorp.dev/docs/offline)).

So the thread's best point, that last-write-wins is not conflict handling, argues for what ilmi built. ilmi's merge takes the later of two schedule lines by their own `last` then `due` fields, keeps both versions of conflicting prose under a notice, and unions the append-only review log ([src/sync/merge.ts](../src/sync/merge.ts)). That is Anki's documented behaviour, where a card "will be kept in the state it was when it was most recently answered" and both reviews stay in the log ([Anki manual](https://docs.ankiweb.net/syncing.html)), without Anki's forced one-way overwrite when a schema changes. Of the surveyed services only Obsidian Sync merges Markdown text automatically as a matter of course, and none applies a rule specific to schedule data. ilmi's known gap is a card reworded on one device and graded on the other, which lands as two blocks under a notice ([PLAN.md](../PLAN.md)). The closest precedent for the migration the thread recommends is Logseq, which explained its move from Markdown to SQLite in April 2024 and by May 2026 still had not shipped two-way Markdown interop ([Logseq forum](https://discuss.logseq.com/t/whats-new-with-logseq-db-may-16th-2026/35020)).

## Two of seven architectures survive large files and the phone

The comparison below scores each candidate on the criteria that matter for a GoodNotes replacement on two or three Apple devices.

| Architecture | Large files | Lazy download on the phone | Conflicts: text / schedule / ink | Build cost from today | Running cost | Lock-in and ownership | Main risk |
|---|---|---|---|---|---|---|---|
| 1. Git for everything (today) | Fails: GitHub blocks objects over 100 MiB | None: libgit2 has no partial clone | Format-aware / later instant / keeps ours silently | Nothing | Free | None | Every device carries every version of every binary |
| 2. Git + Git LFS | Up to 2 GB per file on GitHub Free and Pro | Yes: clones carry pointers under 1 KB | As today, plus pointer-level policy for binaries | Small protocol client | 10 GiB free, then metered | Standard protocol | Rewritten ink can never be deleted on GitHub |
| 3. Git + bucket store | Bound by the bucket, not a git host | Yes: fetch by hash on open | As today, plus app-controlled versions for ink | Small client plus garbage collection | Free to 10 GB on R2, about $0.60 a month at 50 GB | User's own bucket, whole objects | Two sync paths that can drift apart |
| 4. Snapshot protocol on a bucket | Good: chunked and deduplicated | Possible | Whole-file in SiYuan and Joplin; ilmi's merge only if a base is kept | Large: replaces milestones 53–55 | Same bucket | Opaque chunks unless designed otherwise | Lock races and a record of sync corruption fixes |
| 5. SQLite + CRDT sync | Needs a separate blob path anyway | Not addressed | Per-cell last-write-wins, no text merge | Rewrite of format, load path and merge | A relay or server | High: plain files are gone | Unmaintained library, Logseq's precedent |
| 6. Own sync server | Good | Yes | Whatever is built | Server and protocol, then operations | A host to pay for and secure | Self-run | Operations burden for one user |
| 7. File-provider sync | Provider-dependent, files evicted | Provider decides | Whole-file duplicates; ilmi's merge cannot run | Custom Swift plugin | Provider's plan | Low | iCloud is the only route that works on iOS |

**Git for everything** ends where the owner already found it. GitHub blocks any object over 100 MiB and any push over 2 GB ([GitHub repository limits](https://docs.github.com/en/repositories/creating-and-managing-repositories/repository-limits)). The deeper problem is the phone: libgit2 supports shallow fetch but neither partial clone nor sparse checkout, and its partial-clone issue has been open since 2020 with no maintainer commitment ([libgit2 #5564](https://github.com/libgit2/libgit2/issues/5564)). An iPhone clone therefore downloads every PDF and every historical version of every ink page before the vault opens.

**The snapshot protocol** that SiYuan and Joplin use would cost ilmi its best asset. SiYuan resolves conflicts per file, with one version winning and the loser copied to history, and its cloud lock is a read followed by an unconditional write that two devices can both pass ([dejavu sync_lock.go](https://raw.githubusercontent.com/siyuan-note/dejavu/main/sync_lock.go)). Its release notes record a fix for notebook data corrupted during sync ([SiYuan v2.10.14](https://newreleases.io/project/github/siyuan-note/siyuan/release/v2.10.14)). Joplin never merges: the remote note replaces the local one, which moves to a Conflicts notebook ([Joplin conflict help](https://joplinapp.org/help/apps/conflict)). Rebuilding this over a bucket means re-creating what git gives ilmi for free (a merge base, history, and an atomic "push only if nobody else did") and discarding three tested milestones to do it.

**An own server** is what Goodnotes, Notability and Notewise each built between 2024 and 2026, for cross-platform reach, collaboration and independence from iCloud quotas ([Notability Cloud FAQ](https://support.gingerlabs.com/hc/en-us/articles/9598417028378-Notability-Cloud-FAQ)). A single-user Apple-only app needs none of those. A server adds three things a bucket lacks: an atomic commit, an ordered change feed and push. ilmi already has all three for text: a git host refuses a stale push, a fetch is the change feed, and the ntfy nudge ilmi already sends after each push is the notification. Sync is "a few seconds with the nudge, a couple of minutes without" ([PLAN.md](../PLAN.md)), and the later-instant rule for schedule lines covers two devices grading in that window.

**File-provider sync** fails twice. The provider resolves or duplicates a conflict before the app sees both versions, so ilmi's merge cannot run and schedule lines fall back to whole-file last-writer-wins. On iOS, Obsidian supports only iCloud Drive as an OS-level provider ([Obsidian help](https://obsidian.md/help/sync-notes)), which the owner ruled out; Syncthing's iOS client states that "no iOS app can run continuously in the background" ([Möbius Sync FAQ](https://mobiussync.com/faq/)); and Tauri's dialog plugin has no folder picker on iOS ([Tauri dialog plugin](https://v2.tauri.app/plugin/dialog/)).

### LFS or a bucket: the notes disagree, and ink decides it

The notes pull in two directions on where large files should live. The git research favours Git LFS on the same host: the protocol is one JSON request plus a plain HTTPS `GET` or `PUT` per object, a client is a few hundred lines of Rust, clones carry only small pointer files, and the user needs no second account ([git-lfs batch API](https://github.com/git-lfs/git-lfs/blob/main/docs/api/batch.md)). ilmi's own plan leaned the same way ([PLAN.md](../PLAN.md)). The app-level research favours a bucket: Cloudflare R2 charges $0.015 per GB-month with 10 GB and all egress free, which puts a 50 GB library at about $0.60 a month ([R2 pricing](https://developers.cloudflare.com/r2/pricing/)).

For PDFs alone the two are close, because a PDF is written once and never changes. Ink breaks the tie. Every rewrite of an LFS file is a new full-size object, and GitHub's documentation is explicit that removed objects "will continue to count toward your Git LFS storage quota" and that the only removal is to "delete and recreate the repository" ([GitHub: removing files from LFS](https://docs.github.com/en/repositories/working-with-files/managing-large-files/removing-files-from-git-large-file-storage)). The notes disagree about how fast that bites. One illustration puts 200 pages at 50 revisions of 1.5 MB each, about 15 GiB, past the whole 10 GiB free allowance; but the 1.5 MB is an assumption, and no one has measured a PencilKit page. At 150 KB a revision the same library is 1.5 GiB. The evidence therefore supports the mechanism and not the magnitude: growth is monotonic and unreclaimable on GitHub whatever the page size, and that is disqualifying for data that is rewritten every session, while remaining acceptable for PDFs. GitHub's bandwidth allowance is the second constraint: 10 GiB of downloads a month, after which, with no payment method, LFS "is disabled on your account until the next month" ([GitHub LFS billing](https://docs.github.com/en/billing/concepts/product-billing/git-lfs)). Filling two devices from a 10 GB library exceeds it in the first month.

A bucket handles both classes of data with one mechanism, lets the app delete superseded ink, and costs less. Its price is a second credential on each device and a one-time bucket setup. The weight of evidence points to the bucket, with one hedge that keeps LFS open: identify every object by the SHA-256 of its content and its size in bytes, which is exactly what an LFS pointer records ([git-lfs spec](https://github.com/git-lfs/git-lfs/blob/main/docs/spec.md)). Moving to an LFS server later is then a re-upload, not a history rewrite.

## The staged path: memory first, then PDFs, then ink

The recommendation is architecture 3, built in four stages, with architectures 4, 5 and 6 explicitly not built.

### Stage 0: measure on a device and remove the in-memory costs

The measurements found three costs that have nothing to do with Markdown and are cheap to remove. The first is a quadratic lookup: `pagesOf` searches the whole tree once per document, which consumed **6.5 s of a 9.1 s open at 50,000 files** and 413 ms of 3.5 s at 10,000; a path-to-node map makes it constant. The second is the queue: every grade rebuilds it from all documents twice, and then re-reads the entire review log when the app's own append comes back through the file watcher. The rebuilds cost about 10 ms per grade at the sample's size, **150 ms at 11,000 cards and 2 s at 115,000**. Keeping each document's queue items in a map and replacing one entry per change removes the per-document pass, about 30% of the rebuild; rebuilding once per grade halves the rest. The third is the review log, which is loaded whole at open and scanned whole on every queue build to find today's reviews. Ten years at 100 reviews a day is about 365,000 lines, 100 MB of heap and 65 ms added to each rebuild; reading only the current month's file for the daily allowance removes it ([measured for the notes](../research_notes/ilmi%20sync%20and%20storage%20architecture/ilmi_current_storage_and_load_timing.md)).

Memory is the tighter limit on iPad and iPhone. The renderer keeps both the raw text and the parsed form of every document, so heap runs at 3.7 times the Markdown bytes: 15 MB for the sample, 49 MB at 11,000 cards, 381 MB at 115,000. The first two are comfortable; the third is at risk in a mobile web view. Nothing needs building for this yet. What needs doing is the device measurement in the last section, because the owner's real collection has never been imported and its size sets the threshold.

### Stage 1: PDFs leave git for a bucket, fetched on open

Git keeps tracking Markdown, the review log and a small text record of each large file's SHA-256, size and path. The bytes go to the bucket as whole objects named by hash, readable with any S3 tool, unlike SiYuan's opaque encrypted chunks. Each device chooses what to hold: everything on the Mac, a folder or nothing on the phone, with a PDF fetched when its book is opened. This is the pattern DEVONthink's "shallow sync" uses ([DEVONtechnologies](https://devontechnologies.com/blog/20220531-shallow-sync-devonthink-to-go)), and Zotero staff describe its iOS app the same way ([Zotero forum](https://forums.zotero.org/discussion/comment/382216)). Because ilmi never writes a PDF ([FORMAT.md](../FORMAT.md)), the hash is a safe identity and a PDF can never conflict. On ownership, the Markdown moves to any git host by changing a remote, and the bucket is the user's own. The bucket's provider can read the PDFs unless the app encrypts them before upload, which is an optional later layer; the git side needs only a fine-grained token confined to the one repository ([GitHub: personal access tokens](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens)).

Three rules come from other apps' failures. Upload objects before pushing the commit that names them, or another device sees a reference whose object does not exist; stock git-lfs orders its work this way, and MarginNote forum users report annotations arriving without their PDF when two sync paths drift ([MarginNote forum](https://forum.marginnote.com/t/icloud-sync-issue-pdf-is-shared-but-annotations-are-not/10578)). Never keep a binary conflict silently: today `mergeFile` keeps the local binary with no notice ([src/sync/merge.ts](../src/sync/merge.ts)), which is safe only because nothing writes PDFs, and it must become "keep both, with a notice" before ink exists. Do transfers in the foreground first and add a Swift plugin for background `URLSession` second, since iOS continues only HTTPS downloads to a file and uploads from a file once the app is suspended ([Apple: downloading files in the background](https://developer.apple.com/documentation/foundation/downloading-files-in-the-background)).

One design choice is untested in any of the notes and needs a short spike: how git records the reference. The LFS convention puts a pointer file at the PDF's own path, which keeps libgit2 simple but means the working tree holds pointer text where the format promises a PDF "read in place". The alternative is to ignore large files in git and keep their references in a text manifest, which leaves real files in the folder and merges with ilmi's existing line rules. The manifest fits ilmi's plain-folder promise better; neither has been run against libgit2's status and checkout behaviour.

### Stage 2: ink as one drawing per page, merged by stroke

Ink has the opposite profile from PDFs: small, and rewritten constantly. PencilKit signals a change after every stroke, so the save unit must be "page closed" or "idle for some seconds", and the sync unit a session ([Apple: PKCanvasView](https://developer.apple.com/documentation/pencilkit/pkcanvasview)). One drawing per page is the unit every source converges on.

Keep the planned pair of files and give them different roles. The stroke data is the truth for ink; the PNG is a derived picture, regenerated after every merge and never merged itself. Apple's Notes does the same, storing a pre-rendered image beside the drawing for devices that cannot read a newer ink version ([WWDC25: Meet PaperKit](https://developer.apple.com/videos/play/wwdc2025/285/)). The pair must resolve atomically, never one device's PNG with the other's strokes. Ink on PDF pages stays in sidecar files keyed by page, never written into the PDF: Zotero keeps annotations out of the file because otherwise "the entire PDF file needs to be transferred after every change" ([Zotero KB](https://www.zotero.org/support/kb/annotations_in_database)), and Apple's PDFKit offers no way to update a PDF in place ([Apple Developer Forums](https://developer.apple.com/forums/thread/763371)).

For conflicts, handwriting is close to an ideal set: strokes are added, rarely changed, and removed. PencilKit's current documentation gives each stroke a UUID ([Apple: PKStroke](https://developer.apple.com/documentation/pencilkit/pkstroke-swift.struct)), which allows the merge Excalidraw uses: union the strokes by id and honour recorded deletions ([Excalidraw blog](https://plus.excalidraw.com/blog/building-excalidraw-p2p-collaboration-feature)). The drawing blob alone cannot say whether a missing stroke was erased or never seen, so the merge needs either the common ancestor or a list of removed stroke ids. A small text list beside the drawing, unioned like the review log, is the better fit, because it frees the bucket to delete old versions. The merge runs in the Swift plugin on any of the three devices, since macOS can decode a `PKDrawing` even though it has no drawing canvas. Until that merge is proven, the fallback is "keep both pages", which loses nothing. Superseded ink objects are deleted from the bucket after a retention window, which is exactly what GitHub LFS cannot do.

### Stage 3: large PDFs out of the web view's memory

Sync is not the only obstacle to a 500-page scanned textbook. ilmi reads the whole PDF over IPC into the web view and then copies it, so the renderer briefly holds two copies plus pdf.js's own ([src/app/bookPdf.ts](../src/app/bookPdf.ts)). The web view's content process has a hard, undocumented ceiling: WebKit engineers gave 1.5 GB for most iPhones in 2024, more on iPads, and the process is killed with no warning when it is exceeded ([WebKit bug 268816](https://bugs.webkit.org/show_bug.cgi?id=268816)). Canvas memory has its own cap, reported at 224–384 MB depending on device and iOS version ([react-pdf #1020](https://github.com/wojtekmaj/react-pdf/issues/1020)). The first fix stays in the web view: load byte ranges instead of the whole file, keep a small fixed pool of page canvases, cap the pixel ratio, and recover when the content process dies. The second, if a real scan still fails, is a native page layer under the PencilKit canvas in the same Swift plugin that ink needs. PDFKit is not free either: one report measured about 0.7 s of CPU and 2.5 MB per image-only page for text analysis that no public API disables ([bookside #34](https://github.com/NomaDamas/bookside/issues/34)).

### Stage 4: a disposable index, when the numbers ask for it

When a real vault on a real phone shows slow opens or memory pressure, add a SQLite index in the Rust side, one per device, outside the vault's sync and safe to delete. FTS5 is already compiled into rusqlite's bundled SQLite ([libsqlite3-sys build.rs](https://github.com/rusqlite/rusqlite/blob/master/libsqlite3-sys/build.rs)). It holds what the app derives today: per-document info, queue rows, the card-id map, deck rows. Unchanged files then skip reading and parsing at open and need not sit in the renderer's heap. Checking 10,000 files' stamps cost 84 ms, and since every file's mtime after a clone is the checkout time, a content hash is the stricter key.

Vault-wide prose search, which ilmi does not have today, belongs to this stage. The index must apply ilmi's existing fold (decompose, drop combining marks and the tatweel, lower-case) before tokenizing and before querying, and use the `trigram` tokenizer to keep substring matching for Arabic clitics. Trigram cannot match queries under three characters, so short queries fall back to a scan. One cheap fix needs no index: the palette's fuzzy match only lower-cases, so unvoweled Arabic does not find voweled titles there, while the deck search and find-in-page already fold correctly.

## What must be tested on a device before committing

The recommendation rests on Mac measurements and documentation, and several load-bearing facts are unverified. They fall into four groups, in the order they should be tested.

**The existing sync has never run for real.** Every sync test uses a local bare repository; the HTTPS-with-token path "is written but no check exercises it", no real device has been used, and whether the file watcher fires on iOS when a pull lands is unchecked ([PLAN.md](../PLAN.md)). Unmeasured too is how large `.git` grows from a commit a minute and month-long log files re-stored on each commit, and how long a phone takes to clone a year of that history. If libgit2 on an iPhone struggles with a text-only repository, that is the one finding that would reopen architecture 4, built with a conditional write on a single head object, which R2 documents as atomic and Backblaze B2 appears to reject ([R2 S3 extensions](https://developers.cloudflare.com/r2/api/s3/extensions/)).

**Load cost in the real app is unknown in three ways.** Tauri's IPC cost per call was not measured, and open makes about 180 round trips for the sample and more than 20,000 for 10,000 files. JavaScriptCore's parse speed and heap size differ from V8's. No cold-cache run and no real collection were measured. The web view's memory ceiling on current iPads and iPhones is known only from a 2024 bug thread. One run of the app on an iPhone with the owner's imported collection answers all of these, and if IPC dominates, one batched native read replaces thousands of calls.

**Ink has no numbers at all.** The byte size of a handwritten page as a `PKDrawing` and as a PNG at 2× was found nowhere and takes minutes to measure. Unverified also: which OS release introduced `PKStroke.id`, whether ids survive a save and reload, what PencilKit does with duplicate ids, how the pixel eraser's split strokes behave in a union, and whether a `PKCanvasView` can sit above Tauri's web view, which Tauri does not document and no existing plugin demonstrates. Pencil latency in a native canvas against a web canvas was not measured by anyone.

**The transfer path and prices need a trial.** Background `URLSession` against signed bucket URLs, their expiry, and resuming a 500 MB upload after suspension are untested, as is pdf.js against PDFKit on a 500-page scan. FTS5 was timed in memory through Python, not on disk on a phone, and a trigram index at 3.7 times the text may be too large there. GitHub's LFS prices were last confirmed in June 2024, at $0.07 per GiB-month.

## Conclusion

The thread asks the wrong question of ilmi. It treats storage format, query speed and sync as one decision that SQLite settles, and for a browser-based Anki clone with one file per card that bundling is reasonable. ilmi's measurements separate the three. Query speed is an in-memory problem with in-memory fixes. Sync quality depends on merge rules that know what a schedule line is, which no database engine supplies and ilmi already has. Storage format is then free to stay what the owner wanted: a folder a person can read.

What actually blocked a GoodNotes replacement was narrower than "git cannot do this": git is the wrong store for two kinds of bytes, large immutable ones and small churning ones, and both want the same thing, a content-addressed store the app can prune. That reframing also sets the risk. The text path is built and needs proving on a device; the binary path is new but small; and the hard, novel work is stroke-level ink merge, which is worth attempting precisely because its fallback, keeping both pages, loses nothing.
